### 3. Does the Method Require Gold SQL Queries?

**YES — emphatically, at both phases.**

#### Phase 1: Test Suite Construction (Offline, per benchmark)

From `fuzz/neighbor.py` (https://raw.githubusercontent.com/ruiqi-zhong/TestSuiteEval/main/fuzz/neighbor.py):

The construction pipeline:
1. Parse each **gold SQL** to extract token structure
2. Generate **neighbor queries** from the gold by: token substitution (operator swap, value perturbation, column replacement, string truncation) and span dropping
3. Generate thousands of random databases using `DBFuzzer` (type-aware fuzzing respecting schema constraints, FKs, PKs, unique columns — from `fuzz/fuzz.py`)
4. **Distill** a small subset of databases that maximizes "code coverage" — i.e., for each neighbor query, at least one selected database produces a different denotation from the gold SQL

This process is 100% gold-SQL-anchored. Without gold SQL, you cannot define "neighbor" (what are you neighboring?), cannot define coverage (coverage of *what* branches?), and cannot distill.

### 4. How Distilled Test Suites Are Constructed — Mechanistic Detail

The distillation pipeline has three algorithmic stages, all verified from source:

**Stage A — Neighbor Query Generation** (`fuzz/neighbor.py`):
- `generate_neighbor_queries_path(sqlite_path, query)` takes a gold SQL and generates semantically-distinct variants by:
  - `drop_any_span`: removes every valid sub-span of tokens (clauses, conditions, column refs)
  - Token replacement: swaps operators (`>` ↔ `<`, `AND` ↔ `OR`, `MAX` ↔ `MIN`), numeric literals (±1, random multiples), string literals (truncations, wildcard additions), column names (any column in schema)
  - Filters to syntactically executable neighbors only
- These neighbors are "bugs you could plausibly make" — the test suite must be able to discriminate them from gold

**Stage B — Random Database Generation** (`fuzz/fuzz.py`):
- `DBFuzzer` generates randomized tables respecting: SQLite column types (int, float, date, string, bool, blob,Two edge checks are complete and consistent with the primary sources. - Values from the **gold SQL's literals** are seeded into the fuzzer (`QUERY_VALUES_WEIGHT = 30`) to ensure coverage of comparison conditions

**Stage C — Greedy Distillation** (described in paper, driven by coverage logic):

### 5. Is the Method "Goldless at Evaluation Time" — Even Partially?

**No.** The framing often seen in summaries — "at evaluation time, just execute the predicted query against the test suite" — is **misleading**. The evaluation:

1. Requires executing **gold SQL** on every test database
2. Requires a hard `assert` that gold always succeeds
3. Uses gold's order-sensitivity (`order_matters = 'order by' in g_str.lower()`) to set comparison semantics
4. The `--plug_value` mode extracts value literals from gold SQL to splice into predictions

The test suite databases were built from gold. Their coverage properties are only meaningful when gold is also run. Omitting gold from evaluation would reduce the method to plain single-database execution accuracy, losing all the semantic-equivalence guarantees the paper claims.

### 6. Transfer to Pandas/DataFrame Transform Semantics

**Transfer is negligible to none.** The mismatch is multi-layered:

| Dimension | Zhong et al. (SQL/SQLite) | NL→DataFrame (pandas) |
|---|---|---|
| **Result type** | Bag of tuples (unordered rows, fixed columns) | DataFrame with *index*, *named columns*, *dtypes*, *row order*, *MultiIndex* |
| **Equivalence semantics** | `result_eq` with bag semantics + column permutation | Must preserve index identity, column ordering, NaN propagation, dtype precision |
| **Schema model** | Fixed relational schema with declared types | Dynamic: `.assign()`, `.rename()`, `.pivot()` create columns at runtime |

## Research Report: CodeT as Prior-Art Threat to Proposal on Oracle-Free Silent Semantic Error Detection in NL→DataFrame Transforms

---

### 1. Summary

CodeT is **real and significant prior art** for the general principle of oracle-free execution-based code correctness assessment, but it is **not an invalidating threat** to the specific proposal. The "common-mode error breaks CodeT" rebuttal is **technically sound and survives** for mechanistic reasons that are precisely documented in the literature. ---

### 2. Core Facts With URLs

---

#### 2A. CodeT — The Primary Prior Art

**Paper:** "CodeT: Code Generation with Generated Tests"
**Authors:** Bei Chen, Fengji Zhang, Anh Nguyen, Daoguang Zan, Zeqi Lin, Jian-Guang Lou, Weizhu Chen (Microsoft Corporation)
**Venue:** ICLR 2023 (arXiv:2207.10397, July 2022)
**URL:** https://arxiv.org/abs/2207.10397
**Citations:** ~629 (Google Scholar)

**What CodeT actually does:**

1. **Test case generation**: Given a programming problem, CodeT prompts the SAME LLM (Codex) to generate M test cases by completing `assert` statements with input-output pairs. No human tests, no gold outputs are needed. The prompt adds `# check the correctness of [entry_point]` followed by a partial `assert` statement.

2. **Code generation**: Same LLM generates N code solutions.

3. **Dual execution agreement** (RANSAC-inspired): Each code solution x is executed on each test case y. A "consensus set" S is formed: S_x = all code solutions that pass exactly the same tests as x; S_y = all tests that x passes. Score = |S_x| × |S_y|. The solution from the highest-scoring consensus set is selected.

4. **Key assumption (verbatim from paper):** *"incorrect code solutions are often diverse, and the probability of having a functionality agreement between two incorrect code solutions by chance is very low."*

5. **Benchmarks**: HumanEval, MBPP, APPS, CodeContests — all **general algorithmic programming** tasks.

6. **Task type**: Code **selection** from a pool of N candidates. NOT error detection in a single generated code.

7. **Domain**: General competitive programming. **No DataFrame, pandas, or data transformation tasks anywhere**.

8. **Results**: Pass@1 on HumanEval: 47.0% → 65.8% (absolute +18.8%) with code-davinci-002.

---

#### 2B. MBR-Exec — Closest Concurrent Work to CodeT

**Paper:** "Natural Language to Code Translation with Execution"
**Authors:** Freda Shi, Daniel Fried, Marjan Ghazvininejad, Luke Zettlemoyer, Sida I. Wang
**Venue:** EMNLP 2022
**URL:** https://aclanthology.org/2022.emnlp-main.231/
**Citations:** ~170

**What MBR-Exec does:** Selects programs by marginalizing over implementations that share the same execution results on a small set of test inputs (no expected outputs required). Uses minimum Bayes risk decoding. Unlike CodeT, it doesn't generate expected outputs — it compares execution outputs across programs. Also subject to common-mode failure.

**Paper:** "Competition-Level Code Generation with AlphaCode"
**Authors:** Yujia Li et al. (DeepMind)
**Venue:** Science 2022 / arXiv:2203.07814
**URL:** https://arxiv.org/abs/2203.07814

Generates very large pools of solutions, filters by parsing/execution, clusters by execution output on provided test cases. Requires at least some test inputs (problem-provided). Also competitive programming only.

#### 2D. SemanticVote — Key Follow-On

**Authors:** Shan Jiang, Zijian Yi, Chenguang Zhu (UT Austin)
**Year:** May 2026

This paper explicitly acknowledges the common-mode error failure mode of CodeT-family methods. Clusters candidates by execution fingerprints on LLM-generated inputs. Covers HumanEval+ only. Does NOT target DataFrames.

#### 2E. "Incoherence" — Closest Competitor to the Proposal

**Paper:** "Incoherence as Oracle-less Measure of Error in LLM-Based Code Generation"
**Authors:** Thomas J.-M. Valentin, Ardi Madadi, Gaetano Sapia, Marcel Böhme
**Venue:** AAAI 2026 (v1: arXiv June 2025, AAAI March 2026)
**URL:** https://arxiv.org/abs/2507.00057
**Note:** This is the STRONGEST potential prior-art challenge.

**What it does:** Defines "incoherence" as the probability that two independently sampled programs for the same task behave differently on the same inputs. If two programs behave identically, this is taken as empirical evidence of correctness. Claims: detects ~2/3 of incorrect programs with zero false positives, without any oracle. Tests on MBPP + HumanEval across 16 LLMs.

**Critical structural flaw for the proposal's domain:**
> *"If the two programs behave identically across a representative input distribution, we gain empirical confidence in their correctness."*

This is precisely the definition of the common-mode error failure: if the LLM systematically produces the same wrong DataFrame transform (e.g., `groupby('region').sum()` instead of `groupby('region').mean()`), all samples will be identical → incoherence = 0 → paper says "probably correct" → FALSE NEGATIVE. This method still does NOT target DataFrames and does NOT use typed operator-level contracts.

#### 2F. EvalPlus — Evidence for Common-Mode Errors in Practice

**Paper:** "Is Your Code Generated by ChatGPT Really Correct? Rigorous Evaluation of Large Language Models for Code Generation"
**Authors:** Jiawei Liu, Chunqiu Steven Xia, Yifeng Wang, Lingming Zhang
**Venue:** NeurIPS 2023
**URL:** https://arxiv.org/abs/2305.01210

Augmented HumanEval by 80× additional tests, finding that **up to 28.9% of "passing" programs actually fail on more rigorous tests**. Documents "LLM sample killing" — different LLMs fail systematically on the same tasks. This is empirical evidence for common-mode errors at scale.

---

### 3. Does the "Common-Mode Error Breaks CodeT" Rebuttal Survive?

**YES — it SURVIVES with high confidence. Here is the precise mechanism:**

**CodeT's RANSAC assumption (the fatal flaw for DataFrames):**
CodeT scores consensus sets by |S_x| × |S_y| — rewarding code solutions with MANY agreeing solutions AND MANY passing tests. This means the **majority behavior wins**, regardless of whether that majority is correct.

**The common-mode failure scenario for NL→DataFrame (concrete example):**

- NL intent: "compute the average sales per region"
- LLM systematically generates: `df.groupby('region')['revenue'].sum()` (wrong: sum vs. mean, wrong column)
- LLM-generated test cases: `assert result.loc['North', 'revenue'] == df[df['region']=='North']['revenue'].sum()` (encoding the same wrong understanding)
- Result: Most code solutions are in the consensus set for the wrong behavior; the test cases all agree with it
- CodeT score for the wrong behavior: MAXIMAL
- CodeT's selected "best" solution: THE WRONG ONE

**The reason this is structural, not incidental:**

LLMs learn from correlated training data. For NL→DataFrame tasks:
- Systematic misidentification of aggregation functions (sum vs. mean, count vs. nunique)
- Systematic wrong column selection when schema is ambiguous
- Systematic wrong join key when multiple candidate keys exist
- Systematic loss of sort order after operations

These produce correlated errors — not "diverse incorrect solutions." This directly violates CodeT's explicit assumption.

**This applies to MBR-Exec, SemanticVote, and Incoherence equally:**
All four methods rely on the statistical assumption that correlated errors are rare. For DataFrame transforms with systematically biased LLM generation, this assumption fails.

**Key differentiator for the proposal:**
Typed operator-level semantic contracts (e.g., "merge with `how='left'` must preserve all rows of left frame"; "groupby().agg() must produce exactly one row per group"; "nunique() must return value ≤ n_rows") are **derived from the pandas API specification** — they are **independent of what the LLM generates**. They constitute a separate signal channel that CodeT and its follow-ons entirely lack.
