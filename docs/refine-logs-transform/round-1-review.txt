# Novelty Assessment: Detecting Silent Semantic Errors in LLM-Generated Pandas/Dataframe Code (No Gold Outputs, No Tests)

---

## Executive Summary

This proposed paper sits at the intersection of six distinct fields — none of which individually covers its core niche. The closest threats are **DS-1000** and **ARCADE** (which evaluate pandas codegen but use gold outputs/tests), **ExeDS** (execution-based DS evaluation with desired outputs), **SemGuard** (semantic error detection without tests — but on general code, not dataframes), and **Smoke/mlinspect** (operator-level data lineage — but as runtime infrastructure, not LLM verification). The combination of (a) no gold output, (b) no pre-written tests, (c) pandas/dataframe domain, (d) semantic fidelity verification, and (e) typed operator-level attribution is **not covered by any single existing work**. However, the space around it is crowded, and reviewers will attack on all five dimensions individually.

## Area 1: Text-to-SQL Evaluation/Verification

### 1.1 Spider (Yu et al., 2018) — EMNLP 2018
📄 `arxiv:1809.08887` · https://arxiv.org/abs/1809.08887

**What it does:** Introduces a large-scale cross-domain text-to-SQL benchmark (10,181 questions, 200 databases). Primary metric is *exact-match accuracy* against a gold SQL string.

**Covers the proposal's niche?** ❌ **No.** Exact-match is purely structural; it doesn't handle semantic equivalence of alternative correct queries, and entirely depends on a gold query/output. No mechanism for verifying semantic fidelity without a gold reference.

---

### 1.2 Test Suite Accuracy for Text-to-SQL (Zhong et al., 2020) — EMNLP 2020
📄 `arxiv:2010.02840` · https://arxiv.org/abs/2010.02840

**What it does:** Proposes *test suite accuracy* to approximate semantic correctness — generates a suite of database instances, runs both gold and predicted SQL, and checks if outputs match across instances. It distills a small test suite achieving high code coverage.

**Covers the proposal's niche?** ⚠️ **Partially and dangerously so.** This is the closest analogy in text-to-SQL — it moves beyond surface-form matching toward semantic equivalence without relying on a single gold output. However: (a) it **still requires a gold query** to generate the test suite, (b) it is SQL-specific (set/bag semantics, relational algebra), and (c) it focuses on *query equivalence*, not *intent-to-code semantic fidelity* in dataframe pipelines. **Reviewers will cite this as a precursor — you must explicitly acknowledge and differentiate.**

---

### 1.3 BIRD (Li et al., 2023) — NeurIPS 2023
📄 `arxiv:2305.03111` · https://arxiv.org/abs/2305.03111

**What it does:** Large-scale text-to-SQL benchmark with 12,751 pairs and 95 databases (33.4 GB), emphasizing *database value comprehension*, dirty data, and SQL efficiency. Uses execution accuracy. Even ChatGPT achieves only 40.08% vs. human 92.96%.

**Covers the proposal's niche?** ❌ **No.** Execution accuracy against known gold outputs; SQL-only; no mechanism for detecting semantically-wrong-but-executing queries without gold comparison.

---

### 1.4 DAIL-SQL (Gao et al., 2023)
📄 `arxiv:2308.15363` · https://arxiv.org/abs/2308.15363

**What it does:** Systematically compares prompt engineering strategies (question representation, example selection/organization) for LLM-based text-to-SQL; achieves 86.6% execution accuracy on Spider.

**Covers the proposal's niche?** ❌ **No.** A generation/prompting paper, not a verification paper. Gold outputs always present.

---

### 1.5 DIN-SQL (Pourreza & Rafiei, 2023) — NeurIPS 2023
📄 `arxiv:2304.11015` · https://arxiv.org/abs/2304.11015

**What it does:** Decomposes text-to-SQL generation into sub-problems fed back to an LLM; achieves 85.3% execution accuracy on Spider, 55.9% on BIRD.

**Covers the proposal's niche?** ❌ **No.** Same as above — generation with gold-answer evaluation. No goldless verification.

---

### **Key Text-to-SQL Gap:** The "goldless" checking problem has no established solution even in SQL, let alone in pandas. Zhong et al. 2020 is the closest precedent but still requires gold queries to construct test suites.

## Area 2: Data Science/Code Generation Benchmarks

### 2.1 DS-1000 (Lai et al., 2022) — ICML 2023
📄 `arxiv:2211.11501` · https://arxiv.org/abs/2211.11501

**What it does:** 1,000 data science problems across 7 Python libraries (NumPy, Pandas, SciPy, etc.) from StackOverflow. Uses **multi-criteria evaluation**: functional correctness via **pre-written test cases** + surface-form constraints (API usage restrictions). Claims 1.8% false positive rate. Best model (Codex-002) achieves 43.3%.

**Covers the proposal's niche?** ❌ **No.** Requires pre-written test cases AND surface-form constraints. Evaluates *pass/fail*, not *semantic fidelity*. No operator-level attribution, no goldless checking.

---

### 2.2 ARCADE (Yin et al., 2022/2023) — ACL 2023
📄 `arxiv:2212.09248` · https://arxiv.org/abs/2212.09248

**What it does:** 1,082 NL-to-pandas code generation problems in Jupyter notebooks (multi-turn, multi-modal context). Evaluates by executing generated code and comparing output to **gold execution output**. Introduces PaChiNCo (62B pandas-specialized LM).

**Covers the proposal's niche?** ❌ **No — and this is the most dangerous competitor.** ARCADE is the de facto pandas codegen benchmark but: (a) evaluates against **gold execution outputs** from reference notebooks, (b) treats correctness as binary match, (c) provides no operator-level error attribution, and (d) cannot operate without gold outputs. **The proposal must explicitly position against ARCADE.**

### 2.3 ExeDS (Huang et al., 2022) — ACL DaSH Workshop 2022
📄 https://aclanthology.org/2022.dash-1.5/

**What it does:** 534 Jupyter notebook problems with code context, task description, reference program, and **desired execution output**. Shows that models with high surface-form (BLEU/CodeBLEU) scores fail execution, motivating execution-based metrics over string similarity.

**Covers the proposal's niche?** ❌ **No.** Requires a desired execution output as gold. Key insight is that string similarity ≠ semantic correctness — which is philosophically aligned with the proposal, but the solution still depends on gold outputs.

### 2.4 HumanEval (Chen et al., 2021)
📄 `arxiv:2107.03374` · https://arxiv.org/abs/2107.03374

**What it does:** 164 hand-written Python programming challenges, each with a docstring and test cases. Evaluates pass@k over generated samples. The standard code generation benchmark.

**Covers the proposal's niche?** ❌ **No.** Algorithmic problems with pre-written unit tests; no data transformation specificity; no goldless verification.

### 2.5 EvalPlus (Liu et al., 2023) — NeurIPS 2023
📄 `arxiv:2305.01210` · https://arxiv.org/abs/2305.01210

**What it does:** Extends HumanEval by 80× with automatically generated test cases (LLM + mutation-based), building HumanEval+. Finds that prior reported pass@k overstates performance by up to 19-29% due to insufficient tests.

**Covers the proposal's niche?** ⚠️ **Adjacent but not covering.** Makes the important point that test-coverage gaps allow false positives — but fixes this by *adding more tests*, not by detecting errors without tests. **The proposal's contribution is orthogonal:** rather than needing better tests, can we detect semantic errors *without any tests at all?*

**Covers the proposal's niche?** ❌ **No.** Still execution-with-gold-answer evaluation.

## Area 3: Execution-Based Evaluation and Self-Debugging

### 3.1 Self-Debugging (Chen et al., 2023)
📄 `arxiv:2304.05128` · https://arxiv.org/abs/2304.05128

**What it does:** Teaches LLMs to debug their own code via few-shot demonstrations, including "rubber duck debugging" — explaining code in natural language without human feedback. On Spider (no unit tests), improves by 2-3% overall and 9% on hardest problems using code explanation.

**Covers the proposal's niche?** ⚠️ **Important near-miss.** The Spider experiment with no unit tests is directly relevant — the model explains its own SQL and catches errors without a test harness. But: (a) it's SQL not pandas/dataframes, (b) it still uses execution feedback when available, (c) it doesn't attribute errors to specific operators, and (d) it doesn't formalize "semantic fidelity" — it just improves accuracy on the Spider metric.

---

### 3.2 Is Self-Repair Good? (Olausson et al., 2023) — ICLR 2024
📄 `arxiv:2306.09896` · https://arxiv.org/abs/2306.09896

**What it does:** Analyzes Code Llama, GPT-3.5, GPT-4 self-repair on HumanEval and APPS. Finds that self-repair gains are often modest and bottlenecked by the model's ability to provide *feedback on its own code*. Artificially boosting feedback quality dramatically improves repair.

**Covers the proposal's niche?** ⚠️ **Indirectly relevant but supports the proposal.** The finding that "self-repair is bottlenecked by feedback quality" motivates designing better structured semantic-checking signals — which is what the proposal does. However, this paper doesn't address goldless verification or dataframe-specific semantics.

---

### 3.3 CodeT (Chen et al., 2022)
📄 `arxiv:2207.10397` · https://arxiv.org/abs/2207.10397

**What it does:** Uses the same LLM to generate test cases for its own code samples, then selects solutions via dual execution agreement (consistent outputs + agreement with other samples). Lifts HumanEval pass@1 from 47.0% to 65.8%.

**Covers the proposal's niche?** ⚠️ **Critically related — and a genuine threat to novelty.** CodeT operates without pre-written gold tests by using generated tests. However: (a) it still *generates and runs tests*, producing gold-by-proxy outputs, (b) it assumes test cases can be meaningfully generated (hard for complex pandas transformations with real DataFrames), and (c) it doesn't provide operator-level attribution. **The proposal's distinction is that it avoids execution of tests entirely.**

---

### 3.4 TiCoder / Interactive Test-Driven Code Gen (Lahiri et al., 2022)
📄 `arxiv:2208.05950` · https://arxiv.org/abs/2208.05950

**What it does:** Interactive workflow where an LLM generates test cases to formalize user intent, then prunes/ranks code suggestions using those tests. Improves pass@1 on MBPP by 22-38% and HumanEval by 25-54%.

**Covers the proposal's niche?** ❌ **Requires user interaction for test validation** — explicitly interactive, requires lightweight user feedback. Not goldless.

# Ruthless Novelty Assessment

## Where novelty is **real and defensible:**

1. **No-gold + no-test verification for pandas transformations.** This combination is uncovered. All existing pandas/DS benchmarks (DS-1000, ARCADE, ExeDS) require gold outputs. The proposal's core setting is genuinely new.

2. **Typed operator-level attribution.** Neither SemGuard (which gives line-level annotations) nor mlinspect (which is for existing pipelines) provides *typed relational semantics for each pandas operator* as a verification signal. Characterizing groupby aggregation bugs vs. merge key errors vs. filter predicate inversions is not done anywhere.

3. **Semantic fidelity vs. execution correctness distinction.** The paper forces a distinction that the community blurs: code can *execute* without error and still be *semantically wrong* relative to intent. This is strongly motivated by de Santana et al. (2022) and Panko (2010) but not systematically addressed by any ML/NLP paper.

## Where novelty is **fragile — prepare defenses:**

1. **"Why not just use CodeT / generate test cases?"** Reviewers will ask why LLM-generated tests can't replace gold outputs. Response: (a) for dataframes with real data, test generation requires specifying expected output schemas and values, which is as hard as specifying gold; (b) generated tests for pandas code have very low discriminative coverage for semantic errors like wrong groupby keys or unintended left vs. inner joins; (c) CodeT's dual-execution agreement fails when multiple wrong implementations agree with each other.

2. **"SemGuard already detects semantic errors without tests."** Response: SemGuard's SemDiff dataset is for algorithmic code; it has no notion of dataframe schemas, join semantics, aggregation semantics, or the data-dependent behavior of pandas operations. A filter `df[df['a'] > 0]` is syntactically and structurally similar to `df[df['a'] >= 0]` — SemGuard cannot flag this because it doesn't understand the semantic role of the column `a` in the pipeline.

3. **"Test suite accuracy (Zhong 2020) already does goldless SQL checking."** Response: (a) Zhong et al. still needs a gold query to generate test databases; (b) SQL has clean formal semantics (set/bag); pandas operations are stateful, side-effect-prone, and data-dependent; (c) no analogous "pandas equivalence class" theory exists.

4. **"mlinspect already does operator-level checking."** Response: mlinspect detects data *distribution* anomalies (bias, leakage) in *existing, presumably correct* pipelines. It doesn't reason about whether a pipeline correctly implements a stated NL intent — i.e., it can't tell you if `merge(on='customer_id')` was supposed to be `merge(on='order_id')`.

## Bottom Line for the Paper

**The proposal is novel** along the intersection of all five dimensions. The claim space is genuine but the boundaries are razor-thin on three edges:

1. **Against SemGuard:** You must show that general-purpose line-level semantic evaluation is insufficient for pandas because pandas operator semantics are *relational and data-dependent* in ways that require domain-specific typed attribution (schema tracking, join-key semantics, aggregation function semantics, window/groupby scope).

2. **Against ARCADE/DS-1000:** You must prove you can detect errors that execution-with-gold misses (wrong joins producing plausible-looking outputs, wrong aggregation functions on homogeneous data), and that your method works where gold outputs are unavailable (truly novel scripts, proprietary data).

3. **Against mlinspect:** You must show that intent-faithfulness checking (does code implement the NL intent?) is different from distribution-anomaly detection — mlinspect checks if the data flowing through is distributional-correct, not whether the operations match the user's stated intent.

**The strongest possible contribution claim is:** *"We are the first to verify semantic fidelity of LLM-generated pandas transformations by leveraging typed operator-level relational semantics — without gold outputs, pre-written tests, or execution of the generated code."* Every word in that sentence is load-bearing and differentiates from prior work.I’ve got the main adjacency map. I’m now sanity-checking the highest-risk comparators so I don’t overstate novelty or lean on shaky parallels.**Novelty**
1. The core claim is **not already done** by the obvious neighbors, but your current framing overstates the gap.
- **Spider / BIRD / DIN-SQL / DAIL-SQL** are generation benchmarks measured by exact match or execution accuracy against gold queries/outputs. The closest real precursor is **Test Suite Accuracy** (Zhong et al., EMNLP 2020): it moves from string match to semantic equivalence, but still needs a gold query to distill test DBs. That is a precursor, not a collision.
- **DS-1000** (Lai et al., ICML 2023), **ARCADE** (Yin et al., 2022/2023), and **ExeDS** (Huang et al., DaSH 2022) are the closest pandas/data-science lines. They all rely on hidden tests or desired outputs. They do **not** solve “is this transform faithful to intent without gold output?”
- **Self-Debugging** (Chen et al., 2023), **CodeT** (Chen et al., 2022), **TiCoder**, **EvalPlus**: these are about repair, reranking, or generating better tests. They are adjacent, and CodeT is the most dangerous because it weakens the “no prewritten tests” story. But they still reduce correctness to test execution, not typed semantic verification of dataframe transforms.
- **LLM-as-a-Judge** work is not a collision; it is too generic and does not give dataframe semantics or typed attribution.
- **Smoke** and **mlinspect** are infrastructure/inspection ancestors. Smoke gives lineage; mlinspect gives operator-level pipeline inspection for data bugs. Neither verifies NL-intent faithfulness of LLM-generated transforms.

Bottom line: **novel enough for a paper, yes; obviously Oral-novel today, no.** The novelty is in the **intersection**: goldless + no manual tests + dataframe transforms + silent semantic errors + typed operator attribution.

2. Your three differentiators:
- **(a) No gold output / no prewritten tests**: this is the strongest real differentiator. Prior work either uses gold outputs or synthesizes/runs tests. Reviewers will still say “generated invariants are just tests in disguise,” so you must define the distinction precisely.
- **(b) Silent semantic ambiguity**: partly novel. Silent semantic bugs are known in spreadsheets and notebooks, and Jupyter bug-taxonomy work already motivates them. What is new is operationalizing this for **LLM-generated pandas transforms**.
- **(c) Typed operator-level attribution**: novel in this setting. Provenance/inspection work has operator structure, but not attribution of **intent mismatch** like wrong aggregation scope, wrong join semantics, wrong denominator.

**Method Bet**
3. Strongest Oral bet: **(b) intent -> checkable invariants**, backed by a **small operator-semantic library**.
- This is the only path that survives the “both models agree on the same wrong answer” failure mode.
- It also gives the cleanest scientific claim: semantic contracts derived from intent, verified over traced intermediates.

Dead end as primary thesis: **(a) multi-implementation consistency**.
- It is fine as an uncertainty heuristic or abstention signal.
- It is not a publishable core oracle, because common-mode error is exactly what your go/no-go already exposed.

The operator-library path alone is high precision but risky for Oral if it looks like hand-coded benchmark rules. It should be a constrained module inside the invariant story, not the whole paper.

4. The single most important missing experiment: **ambiguity-calibration pairs**.
- For each task, create an ambiguous prompt and a minimally clarified version.
- Show three things: silent error rate drops sharply after clarification; your verifier detects the ambiguous-case failures; and it does not over-flag the clarified controls.
- Without this, reviewers can say you are measuring prompt underspecification, not model semantic failure.

5. The 38%/25% go/no-go evidence is **good pivot evidence, not paper anchor evidence**.
- `n=16` is too small.
- Hand-crafted traps invite “cherry-picked” criticism.
- To make it bulletproof: expand to `50-100` tasks, preregister the ambiguity taxonomy, include real tasks from notebooks/StackOverflow/ARCADE-style contexts, use multiple annotators for intended semantics, include clarified controls, and report across models/seeds.
